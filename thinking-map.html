Inbound BDR Agent — Thinking Map

How I broke the problem down: a single inbound email → six deterministic stages → a fully qualified, researched, and routed AE handoff with zero fabricated data.

Stage Decision Output Fallback / Degradation Design Decision
Input & Normalization
Entry

Normalize
Lead Normalizer → LeadProfile
Extract: senderName, company, title, country, industry, useCase, painPoints, referralSource, statedTimeline

Orchestrator
🧠 Pipeline Orchestrator
Runs stages 1→6 in fixed order. Each stage: validate output via Zod schema → up to 3 retries (fallback model on final attempt) → degrade to "unknown" if exhausted. Events streamed via SSE.
Six-Stage Pipeline
Stage 1
Qualifier
Source: src/agent/stages/stage-1-qualifier.ts
Input: LeadProfile
Output: QualificationResult
• Select best framework: MEDDPICC / BANT / SPICED — justify with ≥2 lead attributes
• Classify every slot as known (with evidence quote + sourceLeadField) or unknown
• Priority score 0–100 with named factor breakdown
• Fit assessment: strong / moderate / weak
Stage 2
Researcher
Source: src/agent/stages/stage-2-researcher.ts
Input: LeadProfile
Output: ResearchReport
• Five dimensions: org_structure, budget_signals, recent_news, leadership_language, positioning
• Live web search (Serper/Tavily/Exa) → fetch top 3 hits per dimension
• Every claim carries: sourceUrl, retrievedAt, verificationStatus
• Provenance-tracked via FetchLedger (URL, HTTP status, timestamp)
• Dimension with zero results → single claim with "unknown" + dimensionsWithNoSource
Stage 3
Responder
Source: src/agent/stages/stage-3-responder.ts
Input: QualificationResult + ResearchReport
Output: EmailSequence (exactly 3 drafts)
• Each email references ≥1 verified research claim
• Each targets 1–2 unknown qualification slots to elicit info
• ≥3 distinct unknown slots covered across the sequence
• Progression rationale on emails 2 & 3
• Zero verified claims → lead-facts-only prompt + researchUnavailableNotice
Stage 4
Case Study Matcher
Source: src/agent/stages/stage-4/ (extractor, scoring-rubric, ranking, serializer)
Input: QualificationResult + ResearchReport
Output: MatchResult
Step 1 — Live Discovery: Crawl FlytBase case-studies index at runtime, extract anchor hrefs, fetch each page, LLM-extract structured CaseStudyRecord
Step 2 — Rubric Scoring: Pure deterministic rubric, four dimensions:
  • industry (0.35) — taxonomy match against lead industry
  • geography (0.25) — country → region match
  • useCase (0.30) — use-case keyword overlap
  • partnerOverlap (0.10) — referral/partner name overlap
Step 3 — Ranking: Score all records, rank 1..n, select winner + runner-up, compute deciding dimensions
live crawl fails?
Fallback
Cached Corpus
Load committed snapshot from src/research/cached-corpus/
Mark all records verificationStatus: "stale"
Emit StageEvent with snapshot timestamp
No Cache
Stage Failed
matchResult = "unknown"
Run continues as partial
Stage 5
GTM Advisor
Source: src/agent/stages/stage-5-gtm-advisor.ts + stage-5/gtm-decision.ts
Input: QualificationResult + ResearchReport + MatchResult
Output: GtmRecommendation
• Search FlytBase public material for partner signals in lead's geography
• Complexity scoring: siteCount, continuousOps, regulatedEnvironment, multiStakeholder, dealSizeIndicator
• Pure decision: direct_ae vs partner_led
• partner_led requires: partnerType + ledgered sourceUrl
• No partner signal → derivedWithoutPartnerEvidence: true
Stage 6
Handoff Generator
Source: src/agent/stages/stage-6-handoff-generator.ts (in progress)
Input: All five upstream outputs
Output: HandoffSummary
• Buyer context paragraph
• Qualification status: priority score, known-field count, unknown slots
• Top 3 verified findings with source URLs
• Recommended case study + why it won
• Suggested next step consistent with GTM motion

Key Design Decisions
Anti-Fabrication
Maybe<T> = T | "unknown"
If a fact can't be verified → literal "unknown"
Never null, never placeholder, never hallucinated
Enforced at compile-time (TypeScript strict) AND runtime (Zod schemas)
degradedOutput() is the single chokepoint
FetchLedger rejects claims with unledgered URLs
Contract Validation
Retry + Fallback Model
Every stage output validated against Zod schema
Up to 3 attempts per stage
Validation errors feed back into next attempt
Final attempt uses fallback model (if configured)
Budget exhausted → "unknown", continue downstream
Pluggable Providers
Swap via env vars, zero code changes
LLM: Gemini / OpenAI / Anthropic / OpenRouter
Search: Serper / Tavily / Exa
Store: Upstash Redis / JSON file
RPM throttle shared across all stages
Rate-limit → graceful degradation, not crash
Proof
Type Safety
npx tsc --noEmit → 0 errors
strict: true, noUncheckedIndexedAccess: true
Zero "as any" casts in UI layer
Every Maybe<T> narrowed with !== "unknown" before property access
Testing
Property-based + Component + Unit
fast-check: artifact round-trip, framework justification, scoring sensitivity, fetch ledger immutability
Testing Library: stage panels, event log, trigger, lead editor
Unit: normalizer, orchestrator, providers
All tests isolated — no network, no live LLM
Transparency
Nothing hidden behind debug toggles
Framework justification: visible text
Scoring rubric breakdown: visible table
Email progression rationale: visible text
Case study match dimensions: visible breakdown
GTM reasoning + complexity signals: visible
All source URLs: clickable links
